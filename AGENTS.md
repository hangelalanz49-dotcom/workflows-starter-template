# Working on this repo in the Base44 sandbox

## What this app is

A single Cloudflare Worker that serves everything on one origin:

- the React client (built by Vite),
- the REST API (`/api/workflow/start`, `/api/workflow/status/:id`, `/api/workflow/event/:id`),
- the `/ws` WebSocket endpoint backed by the `WorkflowStatusDO` Durable Object,
- the `MyWorkflow` Workflow, which pauses on `step.waitForEvent` for a `user-approval` event.

Because it is one origin, the client's relative `fetch("/api/...")` and its
`new WebSocket(.../ws?instanceId=...)` both work unchanged through the preview proxy —
there is no separate API service, CORS setup, or `VITE_API_URL` to configure.

## No credentials required

`@cloudflare/vite-plugin` + `wrangler` emulate Workers, Workflows and Durable Objects
locally on `workerd` (miniflare). No Cloudflare account, API token, or `.dev.vars` is
needed for `npm run dev`, so the sandbox has no secrets. Only `npm run deploy` would
need Cloudflare auth — don't run it here. This means sandbox state (workflow instances,
DO storage) lives under `.wrangler/` in the working directory and is not shared with
any real Cloudflare deployment.

## Running it

```bash
docker compose -f docker-compose.base44.yml up -d
```

The startup command runs `npm ci` before `vite --host 0.0.0.0 --port 5173`, so
dependency changes are picked up by restarting the service — no image rebuild is
needed to change code or deps. Host port 3000 maps to Vite's 5173 (the preview's
fixed entry port).

Vite's host check is satisfied by the platform-provided
`__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS`, passed through bare in compose; no
`vite.config.ts` host allowlist changes were needed. File watching (HMR) works through
the bind mount without polling.

## Verifying it works

Frontend and Worker are compiled on demand, so give the first request a moment.

```bash
# frontend: must contain the React root and the Vite dev client
curl -s http://localhost:3000/ | grep -c 'id="root"'

# worker runtime + API router alive (this 400 is generated by the Worker)
curl -s http://localhost:3000/ws

# full workflow round trip: start -> wait for approval -> approve -> complete
ID=$(curl -s -X POST http://localhost:3000/api/workflow/start | sed -n 's/.*"instanceId":"\([^"]*\)".*/\1/p')
curl -s "http://localhost:3000/api/workflow/status/$ID"          # "running" while paused
curl -s -X POST "http://localhost:3000/api/workflow/event/$ID" \
  -H 'content-type: application/json' -d '{"approved":true}'
curl -s "http://localhost:3000/api/workflow/status/$ID"          # "complete"
```

In the UI, `START` begins a run; the `wait for approval` card shows an **Approve**
button only when the Durable Object broadcasts that step over the WebSocket — that
button appearing is the end-to-end proof that the DO, the Workflow and the `/ws` path
are all live. The approval step waits up to 60 minutes, and after completion the app
resets itself to idle ~1.5s later.

Tests run inside the container (the Vitest Cloudflare pool also uses `workerd`):

```bash
docker compose -f docker-compose.base44.yml exec -T app npx vitest run
```

The second test intentionally forces the approval event to time out, so
`WorkflowTimeoutError` lines in its output are expected, not a failure.

## Quirks

- `worker-configuration.d.ts` is generated by `npm run cf-typegen`; regenerating it
  rewrites a very large file, so only do that when the bindings actually change.
- A `NOSENTRY reporting trace ... HibernatableWebSocketEventInfo` line may appear in
  the dev logs after WebSocket activity. It is a workerd trace warning, not an app error.
